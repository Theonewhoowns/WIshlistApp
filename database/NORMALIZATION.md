# Реляционная модель и обоснование НФБК

## Исправление модели

В первой версии recipient_id был глобальным ключом получателя. Для списка с назначенным
получателем владелец определялся через recipient_id, хотя owner_id также хранился в wishlist.
Для строк с непустым получателем возникала зависимость recipient_id → owner_id,
при этом recipient_id не определял конкретный список. Наличие NULL в личных списках
не позволяет без оговорок применять классические определения зависимостей ко всей
SQL-таблице; однако эта условная избыточность требовала отдельной проверки согласованности.

Исправленная модель сохраняет личные списки и восемь таблиц. Меняется смысл номера
получателя: теперь он уникален только в пределах владельца. Один номер может принадлежать
разным людям у разных пользователей. Новый ключ получателя — (owner_id,recipient_id).
Глобальная уникальность recipient_id больше не является ни ограничением, ни бизнес-правилом.
Автоматическое глобальное генерирование номера получателя удалено.

Пример допустимых записей:

| owner_id | recipient_id | name |
|---:|---:|---|
| 2 | 1 | Мама Ивана |
| 3 | 1 | Папа Анны |

Из одного recipient_id=1 определить владельца нельзя. Список хранит владельца и
необязательный локальный номер получателя; вместе они ссылаются на составной ключ.
Для личного списка recipient_id остаётся NULL. owner_id при этом обязателен и
проверяется отдельной ссылкой на app_user. Необязательная часть составной ссылки
на получателя обрабатывается обычным MATCH SIMPLE (если recipient_id NULL,
наличие получателя не требуется).

В recipient_interest добавлен owner_id, потому что там теперь необходимо хранить
полный ключ получателя. Его нельзя определять только по локальному recipient_id.

## Реляционные схемы

1. app_user(user_id, username, password_hash, password_salt, password_iterations, role)
2. recipient(owner_id, recipient_id, name, age)
3. wishlist(wishlist_id, owner_id, recipient_id, name)
4. wish_item(wish_item_id, wishlist_id, source_idea_id, title, description, planned_price, image_path, is_purchased)
5. gift_idea(gift_idea_id, title, description, min_price, max_price, min_age, max_age, occasion, image_path, is_active)
6. interest(interest_id, name)
7. recipient_interest(owner_id, recipient_id, interest_id)
8. gift_idea_interest(gift_idea_id, interest_id)

## Ключи и функциональные зависимости

НФБК: для каждой нетривиальной функциональной зависимости X → Y множество X должно
быть суперключом отношения. Зависимости определяются правилами предметной области
для всех допустимых состояний, а не случайными совпадениями в демонстрационных данных.

В таблице ниже A означает все атрибуты соответствующего отношения.

| Отношение | Кандидатные ключи | Зависимости, порождающие остальные нетривиальные зависимости |
|---|---|---|
| app_user | user_id; username | user_id → A; username → A |
| recipient | (owner_id,recipient_id) | (owner_id,recipient_id) → name,age |
| wishlist | wishlist_id; (owner_id,name) | wishlist_id → A; (owner_id,name) → A |
| wish_item | wish_item_id | wish_item_id → A |
| gift_idea | gift_idea_id | gift_idea_id → A |
| interest | interest_id; name | interest_id → A; name → A |
| recipient_interest | (owner_id,recipient_id,interest_id) | Нетривиальные зависимости от собственных подмножеств ключа отсутствуют |
| gift_idea_interest | (gift_idea_id,interest_id) | Нетривиальные зависимости от собственных подмножеств ключа отсутствуют |

Уникальность текстовых ключей действует без учёта регистра. Это более сильное
ограничение, чем уникальность точного текста: username, name и пара (owner_id,name)
остаются ключами и при рассмотрении обычного равенства строк.

### app_user

Логин уникален; сведения о пароле и роль принадлежат конкретной учётной записи.
Нет бизнес-правила, по которому роль, соль, хеш или число итераций однозначно определяют
пользователя либо друг друга. Например, число итераций в тестовых данных одинаково,
но не обязано быть одинаковым у всех будущих учётных записей. Все нетривиальные
зависимости имеют в левой части ключ или его надмножество: отношение находится в НФБК.

### recipient

Имя и возраст определяются парой владельца и локального номера. Имена повторяются,
возраст не определяет имя, а локальный номер не определяет владельца. Единственный
кандидатный ключ составной; зависимости от его отдельных частей не заданы. НФБК выполнена.

### wishlist

Список определяется глобальным wishlist_id или уникальным названием у владельца.
Получатель не определяет владельца по одному recipient_id. Пара (owner_id,recipient_id)
может соответствовать нескольким спискам и не определяет их названия или wishlist_id.
Личные списки также могут быть многочисленными. Все определяющие множества в
нетривиальных зависимостях содержат один из кандидатных ключей: НФБК выполнена.

### wish_item

Все свойства желания определяются wish_item_id. Список содержит много желаний;
одинаковые названия допустимы; одна исходная идея может использоваться многократно.
Название, описание и планируемая цена — пользовательский снимок, который можно менять.
Поэтому source_idea_id не определяет title, description или planned_price желания.
Иных зависимостей, кроме зависимостей от ключа, нет: НФБК выполнена.

### gift_idea

Название идеи не уникально. Все свойства определяются gift_idea_id. Правила порядка
границ цен и возраста являются ограничениями допустимых значений, а не зависимостями,
определяющими одну границу по другой. НФБК выполнена.

### interest

Идентификатор и уникальное название взаимно определяют друг друга. Обе стороны
являются кандидатными ключами: НФБК выполнена.

### Связующие отношения

У получателя несколько интересов, у интереса несколько получателей; у идеи несколько
интересов, у интереса несколько идей. Нет ограничений, делающих часть составного
ключа определителем оставшейся части. Повторная пара назначений запрещена полным
первичным ключом. Оба отношения содержат только атрибуты своих составных ключей,
и по установленным правилам нет зависимостей от их собственных подмножеств: НФБК выполнена.

Итог: при перечисленных правилах предметной области все восемь отношений соответствуют
НФБК. Это обоснование не заменяет запуск SQL-проверок ограничений на обеих СУБД.

## Соответствие типов

Идентификаторы и локальные номера — INTEGER/INT. Возраст — SMALLINT.
Стоимость — NUMERIC(12,2)/DECIMAL(12,2). Флаги — BOOLEAN/BIT.
Текст имеет ограниченную длину; для SQL Server русский текст хранится в NVARCHAR.
Пути к изображениям необязательны; графические файлы не включены в эту версию базы.
Итоги списков и оценки совпадений не хранятся: вычисляются запросами.

## Поправка логической модели в Oracle Data Modeler

1. В AppUser → Recipient включить Identifying. Основной UID Recipient должен
   состоять из recipient_id и связи с AppUser (перенесённого user_id/owner_id).
2. recipient_id остаётся обязательным числом, но перестаёт быть самостоятельным UID.
   Не оставлять отдельного Unique Key только на recipient_id.
3. Связь Recipient → Wishlist должна переносить составной ключ; уже существующий
   owner_id списка сопоставить с владельцем получателя, не создавать owner_id_2.
   Идентифицирующей эту связь делать не нужно: ключ списка остаётся wishlist_id.
4. Связь Recipient ↔ Interest по-прежнему N:M. При преобразовании её таблица
   получает полный составной ключ получателя плюс interest_id.

В DBeaver результат миграции отобразится после обновления метаданных и диаграммы.
